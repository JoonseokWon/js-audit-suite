# GLA·FIA·현금분석 사용안내

v1.5는 현재 업무의 원장·시산표·리드에 GLA·FIA·현금분석을 연결하고 검토후보에서 추가자료 요청과 조서로 이동하는 로컬 프로그램이다. 기존 12개 모듈을 유지하여 공통업무는 15개 모듈이다. 별도 9개 계정군·33개 증빙연습은 독립 사례이며 현재 공통 TB에 더하지 않는다.

이 안내는 새 분석과 검토 흐름을 설명한다. 기존 금융상품·매출·감가상각·리스·ECL·재고평가·급여·미기록부채·재무제표 등의 상세 계산 범위는 해당 모듈 안내를 함께 확인한다. 분석 결과로 실제 수행·판단·조정 승인·검토가 자동 완료되지는 않는다.

## 1. 통합 더미업무에서 흐름 확인

상단 **통합 더미업무**를 누르고 저장할 상위 폴더를 선택한다. 새 합성 업무를 만들고 원장부터 기존 계산, 원천·재무제표, GLA·FIA·현금분석을 순서대로 실행한다. 완료 후 **자료·검사**에서 각 모듈의 입력·실행시각·차단·검토 건수를 본다.

정상 더미에서도 주말·월말·고액·반복 등 설정 조건에 맞으면 후보가 나온다. 후보가 0이어야 정상이라는 뜻은 아니다. 차단 없이 현재 원장에 연결되었는지와 별도로, 후보의 근거·정상 사유·추가절차를 검토한다.

**원장·리드**에서는 계정 잔액과 모듈 대사, **결과 상세**에서는 분석표와 원문 위치를 확인한다. 이번 분석의 입력 원장과 현재 업무의 원장이 다르면 위험 검토를 정상 완료로 표시하지 않는다. 전체 입력은 KRW 확정값이며 기본 한도는 시트당 10,000행이다. 행수 한도와 실제 실행속도는 구분하고 성능은 해당 검증 기록을 따른다.

## 2. 필요한 자료와 바로 넣는 파일

실제 업무는 **새 업무**에서 회사·기간을 등록하고 먼저 **원장·리드**를 실행한다. 원장 입력의 독립 통제와 추출 근거를 확인한 뒤 아래의 전체 분석 양식을 준비한다.

| 모듈 | 바로 등록하는 전체 입력 | 추가 원천자료 |
|---|---|---|
| GLA | 공통 원장 7시트 + GLA설정 | 원장 계정·작성자·적요·전기일과 검토 임계값의 근거 |
| FIA | 공통 원장 7시트 + FIA설정 + 전표메타 | 시간대가 있는 ERP 입력·승인 로그, 수동/자동 구분, 부서·시스템, 마감·업무시간 정책 |
| 현금분석 | 공통 원장 7시트 + 분석설정·현금계좌·은행거래·은행독립통제·현금원장선택·현금배부·거래처계좌·지급근거·계좌변경 | 은행 원문·추출통제, 계좌 목록, 거래처 지급계좌·변경 증거, 지급근거와 승인 범위 |

공통 7시트는 `설정`, `시산표`, `총계정원장`, `계정매핑`, `독립통제`, `감사조정`, `모듈연결`이다. 현재 업무의 원장 사본과 같은 의미의 값·모집단을 가져야 한다. 분석 자료 안에 다른 회사·기간·원장 금액을 넣거나 모듈연결 설정을 임의로 바꾸면 연결이 차단된다.

원천 분해본은 `raw_analytics/`에 있다. 기존 정상 합성 입력을 목적별로 나눈 같은 시나리오의 자료이며 ERP·은행에서 새로 수집한 독립 증거가 아니다.

| 파일 | 구성 |
|---|---|
| 00_분석자료요청목록.xlsx | 모집단·키·날짜/시간·통제·제출형태 등 19개 요청항목 |
| 01_GL_TB_합성원천.xlsx | 현재 정상 분석 입력의 공통 원장 7시트 |
| 02_ERP전표로그_합성.xlsx | FIA설정·전표메타 2시트 |
| 03_은행현금_합성원천.xlsx | 계좌·은행·통제·배부·거래처·지급근거·변경 이력 등 9시트 |
| 04_GLA_정책.xlsx | GLA설정 1시트 |

분해한 4권·19시트·464개 데이터행을 재결합하여 정상 분석 입력 3권과 값·타입·순서가 일치하고 변경·누락 0임을 확인했다. 단위 테스트도 464개이지만 데이터행과 검사 건수는 다른 단위다. `manifest.json`과 `verification.json`에 모본·파일·물리행 해시와 비교 결과를 남겼다. 구 v1.3 파일의 감사조정 null 서식행과 분석 입력의 헤더 전용 시트 차이는 별도 기록했으며 원본은 변경하지 않았다.

**은행 원천파일 또는 메타파일 하나만 선택하여 분석을 실행하는 형식은 아니다.** 검증한 원장 7시트와 해당 전용 시트를 합친 전체 양식을 사용한다. 원천 내용에서 알 수 없는 값을 임의로 채우지 않는다.

상단 **자료 복사**로 기존 입력양식과 더미자료를 복사할 수 있다. 전체 정상 분석 예시는 `samples/통합/통합_v1.5_GLA.xlsx`, `통합_v1.5_FIA.xlsx`, `통합_v1.5_현금분석.xlsx`다. 원천 분해본이 이 버튼의 복사 대상에 포함되는지는 해당 배포의 자료목록을 확인한다.

## 3. GLA 결과 읽기

**자료·검사 → GLA → 파일 선택 → 등록·검사 실행** 순서로 등록한다. **결과 상세**에서 다음 표를 선택한다.

- `월별집계`, `계정별집계`, `작성자별집계`: 전체 원장 행·전표 수와 차대·순변동을 집계한다. 0원 TB 계정도 남긴다.
- `전표계정조합`, `계정조합`: 전표 단위의 차변·대변 계정집합을 확인한다. 복합 전표나 같은 계정의 분할 행을 임의의 행별 1:1 거래로 만들지 않는다.
- `검토후보`: 주말 전기일, 월말 전기일, 고액, 같은 계정·차대금액 구성의 반복을 설정대로 표시한다.
- `반복그룹색인`: 반복 그룹 전체 구성원을 한 번에 확인한다. 개별 후보의 짧은 사유와 그룹 ID를 함께 읽는다.
- `규칙검토범위`: 적용·미적용 규칙과 데이터가 없어 확인할 수 없는 범위를 본다.

GLA설정의 사용/미사용, 월말까지 남은 일수, 전표 차변합계의 고액기준, 반복 최소횟수를 명시한다. 차변과 대변을 더하여 거래 규모를 두 배로 표시하지 않는다. 월별 전체 원장 변동은 현금흐름이 아니며 작성자 문자열만으로 실제 로그인 계정·수동 전표·승인을 확인할 수는 없다.

주말·월말·같은 구성의 반복은 정기 거래와 결산에서도 발생한다. GLA는 없는 입력시각으로 심야 입력을 판단하거나 적요로 수동 여부를 추정하지 않는다. 이 정보는 명시적 메타를 받은 FIA에서 별도로 확인한다.

## 4. FIA 결과 읽기

전표메타는 회사코드+전표ID+행ID로 전체 원장 행에 정확히 한 번씩 연결한다. 입력시각·입력자·전표유형·승인상태, 승인 시 승인자와 승인시각을 입력한다. 부서·원천시스템·명시적 재분류그룹도 함께 받는다.

입력·승인시각은 예를 들어 `2027-01-05T10:00:00+09:00`처럼 시간대가 있어야 한다. 원장의 `전기일`을 입력시각으로 복사해서는 안 된다. 한 전표의 메타가 행마다 충돌하거나 필수 메타가 누락되면 차단한다. 부서·시스템·승인·유형 등이 미확인인 경우 관련 규칙의 미확인을 남기며 사실을 추정하지 않는다.

FIA설정에는 규칙버전·정책명·마감시각·메타추출시각·고정 시간대·업무시작/종료, 수동 집중의 최소 전표수/금액/비율, 반복 재분류 횟수와 선승인허용 정책을 명시한다. 자정을 넘는 업무시간 구간과 지역별 일광절약시간 자동 전환은 지원하지 않는다.

`전표메타대사`에서 원장 전기일과 실제 입력·승인시각을 나란히 보고, `규칙적용`에서 조건·대상 수·후보·미확인을 확인한다. 후보는 다음과 같은 명시 조건에 따른 검토 대상이다.

- 명시한 마감 후에 과거 업무기간 전기일로 입력
- 입력자별 수동 전표의 건수·금액·비율 기준을 모두 충족
- 승인 상태에서 입력자와 승인자가 동일
- 입력·승인이 추출시각 후이거나 승인 시각·상태·선승인 정책이 맞지 않음
- 명시한 시간대와 업무시간 구간 밖 입력
- 명시 재분류그룹과 계정 방향이 반복되거나 수동전표 승인이 미완료

연말 전기·익년 입력이어도 결산 마감 전의 정상 후속 입력이면 마감후 전기로 잡지 않는다. 사전 승인을 허용한 정책과 금지한 정책도 구분한다. 휴가·공휴일·개인 활동·의도·부정을 추정하지 않는다. 동일 입력자·승인자라고 해도 실제 권한과 별도 검토 근거를 확인해야 한다.

## 5. 현금분석 결과 읽기

분석설정의 대상 GL계정과 제출 계좌 범위를 먼저 확인한다. `현금원장선택`에는 명시한 대상계정 GL행을 빠짐없이 한 번씩 선택하고, `현금배부`에서 은행거래와 원장 복합키의 연결 금액을 명시한다. 같은 금액이라는 이유로 프로그램이 자동으로 맞추지 않는다.

| 결과 표 | 확인할 내용 |
|---|---|
| 현재원장연결 | 분석 입력과 현재 업무의 실제 원장·TB 일치 |
| 현금검사통제 | 계좌별 독립 행수·총입출금·추출 근거 및 입력 통제 |
| 계좌잔액대사 | 은행 기초+입금−출금=기말, 장부/TB 기초기말과의 차이 |
| 현금배부표 | 제출한 다대다·분할 연결의 금액과 실제 원문 행 |
| 은행장부잔여 | 은행·장부의 미배부·부분배부 잔여. 1원도 숨기지 않음 |
| 검토후보 | 반복 일회지급, 승인총액 초과, 확인 가능한 외부 지급계좌 집중, 변경 직후 지급 등의 조건 |
| 규칙미확인·현금분석범위·현금모집단 | 없는 자료, 분모에서 제외한 범위, 제출 계좌와 대상 GL행 |

은행의 독립 행수·총입출금이나 기초기말 산식이 틀리면 차단한다. 중복·고아 참조·타 계좌 배부·반대 부호·과배부·명시 메타 모순도 보완해야 한다. 은행과 TB의 잔액 차이 또는 일부 미대사는 시차·미결제·누락 등을 조사할 검토사항이다. 부분 지급은 잔여를 남기며 자동으로 거래를 완료 처리하지 않는다.

반복 일회지급과 합법적인 정기·분할 지급은 제출된 유형·근거·승인 범위로 구분한다. 주요 공급처의 계좌 집중은 정상일 수 있다. 명시한 자금이체는 자사 계좌 목록, 반대 은행 입금과 양쪽 GL 배부를 함께 확인한다. 계좌 이름이 비슷하거나 소유자가 같다는 사실만으로 분류하지 않는다.

**제출된 선택 계좌의 통제를 맞춘 것과 회사 전체 은행계좌의 완전성을 확인한 것은 다르다.** 완전히 빠진 계좌·은행·기간·지급근거, 원문 진위와 실제 수취인은 별도 계좌목록·조회·은행 원문·권한 증거 등으로 확인한다. 계좌변경 이력 미제출은 변경 없음이 아니다.

## 6. 검토후보에서 자료요청과 조서로

상단 탭 **검토후보**에서 행을 선택하면 모듈, 규칙, 우선순위, 사유, 현재 원장 연결상태와 조서 ID가 보인다. 상세 영역에서 원문 위치·조건·규칙 설정과 버전·후속 확인을 읽는다. 원본 값은 **결과 상세**의 해당 입력표와 업무 폴더에 보존한 사본에서 확인한다.

**관련 조서 열기**는 GLA의 G01, FIA의 I01, 현금분석의 H01로 이동한다. 검사한 모집단과 선정, 실제로 확인한 원문·추가 증거, 정상 사유나 예외 원인, 회계처리 영향과 후속 판단을 직접 작성한다. 자동 입력된 계산 범위는 실제 수행기록이 아니다.

**자료요청 초안**은 후보 사유·원문·후속 확인·자료ID와 해시를 **자료요청** 탭에 채운다. 요청처는 사용자가 입력하고 기한·범위도 확인한 뒤 **요청·수령 기록 저장**을 누른다. 초안을 여는 것만으로 저장이나 발송을 완료하지 않는다. 후보의 원래 입력자료는 분석 근거이며 새로 요청한 자료를 받은 증거와 구분한다.

받은 파일은 **증거·검토의견 → 증거 파일 등록**으로 보존하고 요청에 연결한다. 요청·부분수령·수령·검토완료·취소 상태와 처리내용을 기록한다. 수령 관련 상태에는 등록한 증거가 필요하고 미완료 요청은 검토완료본 출력을 차단한다. 취소할 때도 이유와 범위를 남긴다.

원장이나 분석자료를 바꾸면 기존 후보의 실행과 현재 원장이 달라질 수 있다. **차단·재실행 필요** 상태에서는 최신 자료로 분석을 다시 실행한다. 이전 후보의 초안이나 검토기록을 최신 실행에 그대로 유효한 것으로 취급하지 않는다. 연결된 조서는 다시 저장하고 검토를 요청한다.

## 7. 검토맥락 JSON과 실제 AI 기능의 구분

**검토맥락 저장**은 현재 업무·검토후보·원문 위치·필요자료·버전 해시를 JSON 파일로 보관한다. 파일의 `uses_ai_inference:false`와 실행방법에 로컬 규칙이라는 점을 명시한다. 이 기능은 생성형 AI 응답이나 자동 감사 결론을 만드는 기능이 아니다. 앱에서 외부 AI 호출·자료 전송을 실행하지 않는다.

공개 감사기술의 위험 추천과 사람의 검토 흐름은 자체 화면 설계의 참고다. EY 내부 코드·모델을 사용하거나 실제 EY 도구를 실행하는 프로그램은 아니다. 공식 출처와 참고 범위는 [최근 감사분석·AI 참고](최근_감사분석_AI_참고.md)에서 확인한다. 이 참고문헌을 한국 회계감사기준 준수 인증으로 읽지 않는다.

## 8. 조서 저장·검토·보관

**검토중 저장**으로 계산표·후보·적용 규칙·증거·자료요청·수행검토 조서·변경이력을 Excel 초안에 남긴다. 실제 수행내용, 결론, 검토자와 검토내용은 사용자가 입력한다. **조서 저장·개정 → 검토 요청 → 작성자와 다른 검토자의 검토기록 완료** 순서로 처리한다.

최신 자료에서 차단이 남거나 원장 연결 미확인, 필수 조서 누락, 미해결 의견·자료요청, 자료변경 후 재검토가 남으면 검토완료본을 저장할 수 없다. 출력상태는 선택한 조서의 검토기록 상태이며 전체 감사 완료·감사의견 발행이 아니다. 이름 입력은 인증된 전자서명이 아니며 자동 전기나 조정 승인은 하지 않는다.

업무 폴더의 `업무.sqlite3`, `이력헤드.json`, `원본/`을 함께 백업한다. 이미 저장한 Excel은 정적 값이므로 원본 변경 시 자동 갱신되지 않는다. 다시 실행·수행·검토하고 새로 저장한다.

## 9. 더미와 소스 검증 재현

신규 더미의 구성은 GLA 12·FIA 22·현금 28, 총 62개 파일 사례다. 정상뿐 아니라 위험 조건, 정상 유사거래, 누락·중복·타회사/기간·원장 불일치를 포함한다. `samples/감사분석/cases.json`과 각 폴더의 `cases.json`을 확인한다. 기대 코드는 별도 검증용이며 분석 입력으로 주입하지 않는다.

일부 사례는 원장 자체가 다른 정상 대조군을 사용한다. 사례에 `current_ledger`가 있으면 동반한 순수 원장 7시트 파일을 먼저 별도 업무에 등록한 뒤 그 사례의 분석 XLSX를 실행한다. 기존 통합 원장에 독립 대안 사례를 더하면 안 된다.

```powershell
python -m pip install -r requirements.txt
python tools/prepare_v15_samples.py
python tools/prepare_v15_raw.py
python -m unittest discover -v
python tools/verify_headless_v15.py --output-dir 검증/직접재현_v15_headless
python app.py --self-test-v15 --report 검증/직접재현_v15_UI/report.json
```

화면 없는 검사는 새 폴더 또는 빈 출력 폴더를 사용한다. UI 검사는 실제 창과 합성 업무·Excel을 만들며 검사 코드가 쓴 수행·검토 기록은 테스트용 합성 기록이다. Windows 개발 환경에서의 소스 검사, EXE 검사, 다른 PC·깨끗한 OS 확인은 구분한다.

현재 소스 검증에서 단위 464개와 기존 270+신규 62=전체 332파일 사례·화면 없는 검사 1,949항목이 통과했다. 기록은 `검증/단위검사.txt`, `검증/headless_1/report.json`에 있다. 소스 UI·EXE와 원격 CI는 이 결과와 구분하고 **해당 배포 검증 보고서**에서 완료 상태·EXE SHA256·소스/EXE 결과 일치를 확인한다.

GLA는 `gla/verification/benchmark_10000.json`에 별도 성능 검증을 기록했다. Windows 11·Python 3.14.8 개발 PC의 한 번의 소스 실행에서 10,000원장행·4,993전표를 빠짐없이 검사하고 4,984개 후보를 남겼다. XLSX 읽기·원장 검증·집계·후보 생성은 약 2.385초였고, 시험 XLSX를 만드는 시간은 별도로 약 20.632초였다. 32개 확인 항목을 통과했고 10,001행 입력은 한도 초과로 차단했다.

이 측정은 UI·EXE·Excel 내보내기 시간이나 다른 PC의 속도를 측정한 것이 아니다. 같은 생성기가 TB와 통제를 만들었으며 결과 후보는 실제 부정·사용자 수행·독립 증거가 아니다. 시트당 10,000행 지원과 단일 측정값을 10만/100만행 처리나 모든 입력의 속도 보장으로 확장하지 않는다.

원격 검증과 게시 여부는 해당 태그의 [GitHub Actions](https://github.com/JoonseokWon/for-ax-node-project/actions) 및 [v1.5.0 릴리스 기록](https://github.com/JoonseokWon/for-ax-node-project/releases/tag/audit-suite-v1.5.0)에서 확인한다. 비공개 저장소의 권한 범위 안에서 확인하는 배포다.

## 10. 판단 범위

사용자는 회계 요구사항·검증 관점·최종 판단을 담당하고 AI가 코드 구현과 자동 검사를 보조했다. 자동 검사 통과를 사용자의 수동 검증·실제 고객 감사·회계감사기준 준수 인증으로 주장하지 않는다. 동일 생성기의 원장·메타·은행·통제 더미는 독립된 외부 감사증거가 아니다.

독립 33개 증빙연습과 제한된 자동 규칙을 세법·DB 계리·자산 처분/손상·리스 변경·연결·현금흐름·모든 공시 전반의 실무 기능 완성으로 보지 않는다. 기존 재무제표 대사는 조정전·미마감 TB와 선택 범위이며 승인조정을 반영한 최종 재무제표 대사와 구분한다. 모든 후보의 실질과 증거의 충분성·적합성, 최종 회계 판단은 담당 회계사가 검토해야 한다.
